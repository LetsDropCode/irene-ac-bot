# WhatsApp native UX capability audit

Audit date: 18 November 2026. Release disposition: **READY_FOR_REVIEW**, not production certification.

## Repository evidence

Fetched `origin`; base is `5e9a000` (main, admin TT upgrades #4). Local main matched origin/main. Remote admin and monthly-engagement branches were inspected: their functionality is already incorporated by the main-branch squash merges (#4 and #3); no festive-hosting branch or open PR was found. No separate hosting implementation was merged or created. The original working folder contained unrelated reporting changes; implementation uses an isolated worktree on `feature/whatsapp-native-ux-modernisation`.

The baseline already had queued outbound messages, signed webhooks, inbound deduplication, POPIA lifecycle, approved proactive templates, member/admin menus, and the static `app/flows/assets/admin_tt_date.json` calendar (Flow JSON 7.3). Only the first message in a webhook batch was extracted. Delivery callbacks were ignored. Calendar replies were hard-wired to the admin handler. Graph v22.0 was hardcoded in the sender and two setup scripts.

## Compatibility findings and evidence limits

Graph API version, Flow JSON 7.3 and launch `flow_message_version=3` are independent. No Flow asset version change was made. Mocked payload tests prove URL selection and local construction only; they cannot prove Meta acceptance or account eligibility. The Graph versions lifecycle page could not be retrieved, so v22.0 retirement dates and the full v22→v27 change list remain an operator verification gate.

Meta's current [service-message guide](https://developers.facebook.com/documentation/business-messaging/whatsapp/messages/send-messages) requires an open 24-hour service window for free-form messages; outside it, use approved templates. Existing reminder, milestone and recap services retain their approved-template paths. Delayed free-form queue messages may be rejected by Meta; there is no automatic unapproved free-form fallback. The legacy next-day leaderboard remains subject to its existing service-window assumption and must be checked in staging.

The same guide documents messaging-account selection for tokens with access to multiple messaging accounts. This deployment still assumes one account per configured phone/token. [Current webhook guidance](https://developers.facebook.com/documentation/business-messaging/whatsapp/webhooks/reference/messages) also describes users without available phone numbers. The existing member identity model is phone based: BSUID-only incoming messages are safely ignored, not guessed or linked to a member. Account-model and BSUID migration require separate identity work before claiming universal v27 compatibility.

## Carousel recommendation: DEFER

Use existing lists, images and the Irene Shop link for merchandise; use lists for race/club choices. Media template carousels might later suit merchandise or consented sponsor promotions. Catalog carousels add inventory, compliance and operations work that is not justified solely by visual layout. Template approval/category review, media hosting, device testing, consent and current regional/category prices are operational prerequisites; no cost estimate is asserted.

The index confirms that Meta documents several distinct carousel mechanisms. Their detailed pages returned throttling, cache failures or login requirements during this audit. That is insufficient evidence to construct a new send adapter. `WHATSAPP_RICH_CAROUSELS_ENABLED` is reserved, defaults false, and currently activates nothing. Revisit after obtaining the exact Cloud API send contract and account eligibility. Never substitute Business Agent `component_type` payloads or assume template cards are ordinary session messages.
